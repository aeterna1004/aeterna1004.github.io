# Project Rules

## Do NOT Modify Config Files

This project is deployed on **GitHub Pages** with a specific configuration. The following config files must NOT be modified:

- `next.config.mjs`
- `tsconfig.json`
- `postcss.config.mjs`
- `package.json` (do not add/remove dependencies without explicit user approval)
- `.github/` (CI/CD workflows)
- `components.json`

## Only Modify Source Code, Never Commit Build Artifacts

You may freely create or modify files in these directories:
- `app/` — pages, layouts, CSS
- `components/` — React components
- `hooks/` — Custom hooks
- `lib/` — Utilities, constants
- `public/` — Static assets (images, music, etc.)
- `styles/` — Additional stylesheets

> [!WARNING]
> DO NOT commit or retain build artifacts. Directories like `out/`, `.next/`, or `node_modules/` that are generated dynamically during `npm run build` or `npm install` must be ignored or deleted. 
> 
> **Important:** The `next-env.d.ts` file is also automatically modified by Next.js during build/dev. Do not report it as a changed source file. If it gets modified in your Git tree after running a build, run `git checkout next-env.d.ts` to revert it to keep the commit history clean.
> 
> **CRITICAL RULE ON TESTING:** The AI must NEVER run `npm run build` just to verify code. Doing so creates dozens of changed files (in `out/` and `next-env.d.ts`) that pollute the user's workspace. If you need to test the code visually, simply navigate to `http://localhost:3000` assuming the user already has `npm run dev` running. If the server is not running, do not attempt to compile or build—let the user test it manually.

## Visual Effects Physics & Math

When creating new visual effects based on existing ones (e.g. creating `rose-fireworks.tsx` from `romantic-fireworks.tsx`):

1. **Verify Maximum Bounds (maxR):** Different math equations (like Rhodonea curve vs. Heart shape equation) have completely different bounding sizes. If you reuse the same `speedMultiplier` without checking the `maxR` output of your new formula, the new effect may be micro-sized or massive compared to the original. Always mathematically map the new equation's scale to match the original bounding box.
2. **Launch Angles & Centers of Mass:** Equations like the Heart are bottom-heavy and shoot upwards (mostly positive Y or mostly negative Y). Equations like the Rose (Rhodonea curve) are perfectly centralized and shoot uniformly in all 360 degrees. If a symmetric shape replaces an upward-shooting shape, 50% of the particles will shoot downwards, creating the illusion of a "low explosion". You MUST compensate for this by adjusting the initial burst height (launch rocket `vy` and `targetY`).
3. **Particle Size Scaling:** Particles generated by complex math (like multi-layered rose curves) might need larger individual sizes to be visible. Always tune particle variables (`size`, `alpha`, `decay`) contextually.
4. **Natural Trajectories (Avoid Hardcoding Heights):** When adjusting rocket heights (`targetY` or `vy`) to fix "low explosion" illusions, **do not hardcode them to the very top of the screen**. Fireworks are meant to look organic. Always use a generous `Math.random()` range (e.g. between 10% and 45% of the screen height) so some rockets explode high, and others explode naturally at mid-height. This staggered effect is crucial for realism.
5. **Absolute Radius vs. Velocity Expansion (Frame-Time Math):** When switching a particle engine from a velocity-based expansion (`x += vx * dt` indefinitely) to a localized anchor expansion (`x = center + targetR`), be extremely mindful of pixel scale. A velocity of `10` compounded over 100 frames covers massive distance. A `targetR` of `50` pixels is microscopic on a 1080p screen. Always calculate the terminal screen-space occupied by velocity engines before migrating them to absolute pixel radii.
6. **Dynamic Mobile Scaling for Visual Effects:** Always scale particle density smartly on mobile devices based on the *firing intensity*. During "low" ambient intensity, phones and tablets can safely maintain `0.8` of desktop particles. However, during "high" rapid-fire bursts, you MUST drastically reduce the quantity scalar to `0.5` for phones and `0.75` for tablets to avoid freezing the browser or cluttering the screen into an unreadable mess. Never use a static mobile scalar for effects with variable fire rates.
